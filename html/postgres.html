SECTION 01: INTRODUCTION

What is a Database?

Why modern web applications cannot survive on text files or memory alone

FUNDAMENTALS

The File System Problem

Storing app data in JSON or text files fails at scale. Concurrent writes cause data corruption, searches require reading entire files into RAM, and there are no transaction safety guarantees.

The Database Solution

A Database Management System (DBMS) is specialized software engineered to store, organize, index, secure, and retrieve massive volumes of data with sub-millisecond latency and ACID reliability.

Core Responsibilities

Data persistence across server restarts, concurrency control for thousands of simultaneous users, relational integrity enforcement, authentication, and structured query optimization.

Key Takeaway: A database is not just a hard drive folder; it is a high-speed multi-threaded transaction engine engineered to protect data integrity at all times.
SECTION 01: INTRODUCTION

SQL vs NoSQL: Why PostgreSQL?

Relational rigor meets modern document flexibility

INDUSTRY CHOICE

SQL (Relational)

Structured schemas, strict data types, relational joins, foreign keys, and ACID transactions. Ideal for applications with interconnected data, financial records, and clear entities.

NoSQL (Document)

Schema-less JSON documents. Flexible for rapid prototyping, but complex joins must be manually handled in application code and data duplication is common.

Why PostgreSQL Won

PostgreSQL delivers the best of both worlds: rock-solid relational ACID compliance combined with native high-performance JSONB document querying and indexing.

Feature Traditional SQL (MySQL) NoSQL (MongoDB) PostgreSQL
Relational Joins & Foreign Keys Yes Limited ($lookup) Advanced & Optimized
Semi-Structured JSON / Documents Basic JSON text Native BSON Native JSONB (Binary + GIN Index)

SECTION 07: SQL FUNDAMENTALS

DDL: Creating Tables with Constraints

Defining solid table schemas with data integrity guarantees

DDL
SQL — CREATE TABLE users
CREATE TABLE users (
    id BIGSERIAL PRIMARY KEY,
    name TEXT NOT NULL,
    email TEXT UNIQUE NOT NULL,
    created_at TIMESTAMPTZ DEFAULT NOW()
);

PRIMARY KEY

Guarantees unique identification for each row. Automatically creates an underlying B-tree index and enforces NOT NULL.

NOT NULL & UNIQUE

NOT NULL rejects records without a value. UNIQUE prevents duplicate entries (e.g. prevents duplicate customer email registrations).

SECTION 07: SQL FUNDAMENTALS

DML: Updating & Deleting Records

Modifying data safely and the critical danger of missing WHERE clauses

WHERE CLAUSE
UPDATE & DELETE
-- Safe UPDATE with specific WHERE target
UPDATE users
SET name = 'Dara Sam'
WHERE id = 1;

-- Safe DELETE with target ID
DELETE FROM users
WHERE id = 1;
CRITICAL MISTAKE: Omitting the WHERE clause on UPDATE or DELETE executes the operation across EVERY ROW IN THE ENTIRE TABLE!

Soft Deletes Alternative

In production applications, consider soft deletes: UPDATE users SET is_deleted = TRUE, deleted_at = NOW() WHERE id = 1; to preserve audit history and prevent accidental data loss.

SECTION 08: POSTGRESQL DATA TYPES

Core PostgreSQL Data Types

Choosing the optimal type for storage efficiency and data precision

DATA TYPES
NUMBERS

INTEGER / BIGINT

INTEGER is 4 bytes (-2B to +2B). BIGINT is 8 bytes. Always use BIGINT for high-traffic IDs or analytics counters.

FINANCE

NUMERIC(p, s)

Exact decimal representation. Never use FLOAT or REAL for money or currency; always use NUMERIC(12, 2).

STRINGS

TEXT vs VARCHAR

In PostgreSQL, TEXT and VARCHAR have identical underlying performance. Prefer TEXT unless strict character limit enforcement is required.

LOGIC

BOOLEAN & DATE

BOOLEAN stores true/false/null. DATE stores calendar dates (YYYY-MM-DD) without times or timezones.

SECTION 08: POSTGRESQL DATA TYPES

Timestamps: TIMESTAMP vs TIMESTAMPTZ

Why you should almost always use TIMESTAMPTZ in modern web apps

TIMEZONE SAFETY

TIMESTAMP (Without Time Zone)

Stores naive local time without any timezone offset. Leads to severe bugs when servers, databases, and users reside in different timezones.

TIMESTAMP '2026-10-19 14:00:00' -- Ambiguous: Is this UTC? EST? ICT (Phnom Penh)?

TIMESTAMPTZ (With Time Zone)

Internally converts and stores the timestamp in UTC. When queried, PostgreSQL formats the output based on the client session timezone.

TIMESTAMPTZ '2026-10-19 14:00:00+07' -- Stored internally as UTC: 2026-10-19 07:00:00 UTC
Golden Production Rule: Always declare timestamp columns as TIMESTAMPTZ DEFAULT NOW(). Your database remains strictly normalized in UTC across all global deployments.
SECTION 08: POSTGRESQL DATA TYPES

JSONB: Semi-Structured Power

Storing, indexing, and querying JSON inside relational tables

JSONB
SQL — Querying JSONB
-- Create table with JSONB column
CREATE TABLE user_settings (
    user_id BIGINT PRIMARY KEY,
    metadata JSONB NOT NULL DEFAULT '{}'
);

-- Extract as JSON object (->) vs TEXT (->>)
SELECT 
    metadata->'theme' as theme_json,
    metadata->>'theme' as theme_text
FROM user_settings
WHERE metadata->>'newsletter' = 'true';

JSON vs JSONB

JSON stores raw text. JSONB parses JSON into a decomposed binary format that supports fast indexing, fast key lookups, and rich operators.

GIN Indexing on JSONB

You can build GIN (Generalized Inverted Index) on JSONB columns: CREATE INDEX idx_meta ON user_settings USING GIN (metadata); for blazing-fast document lookups.

SECTION 09: PRIMARY KEYS & UUID

Primary Keys: BIGSERIAL vs UUID

Comparing auto-incrementing sequential integers with distributed UUIDs

PRIMARY KEYS

BIGSERIAL (Auto-Increment Integer)

Fast, 8-byte compact storage, natural ordering. Downside: URLs expose sequential IDs (`/users/1`, `/users/2`), allowing ID enumeration attacks.

id BIGSERIAL PRIMARY KEY

UUID (Universally Unique Identifier)

128-bit globally unique identifier. Can be generated on the client or server without coordinating with the database. Impossible to guess.

id UUID PRIMARY KEY DEFAULT gen_random_uuid()
Criteria BIGSERIAL UUID
Storage Size8 bytes16 bytes
URL Enumeration AttackVulnerable (/orders/42)Secure (impossible to guess)
Client-Side GenerationNo (must ask database)Yes (generate before insert)
Index Insert PerformanceHigh (sequential append)Moderate (random B-tree page splits)
SECTION 09: PRIMARY KEYS & UUID

Generating UUIDs & Tradeoffs

Using gen_random_uuid() and understanding B-Tree page fragmentation

gen_random_uuid()
SQL — Native UUID Generation
-- PostgreSQL 13+ built-in function
SELECT gen_random_uuid();
-- Output: c9a646d3-9c61-4cd7-bf53-73d8f7634f19

-- Creating table with UUID primary key
CREATE TABLE projects (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    title TEXT NOT NULL,
    created_at TIMESTAMPTZ DEFAULT NOW()
);

gen_random_uuid()

PostgreSQL 13+ includes `gen_random_uuid()` natively without requiring the `pgcrypto` extension. Generates cryptographically secure UUIDv4.

UUID Performance Tradeoff

Random UUIDv4 values cause random index insertions, leading to B-Tree page splits and higher write amplification compared to sequential integers.

SECTION 10: RELATIONSHIPS

Database Relationships & Cardinality

Modeling 1-to-1, 1-to-Many, and Many-to-Many associations

CARDINALITY

One-to-One (1:1)

One user has exactly one profile. Enforced with a UNIQUE foreign key.

users (id) ← (user_id UNIQUE) profiles

One-to-Many (1:N)

One user authors many posts. Standard foreign key on the posts table.

users (id) ← (user_id) posts

Many-to-Many (N:M)

Posts have many tags; tags belong to many posts. Resolved via a junction table.

posts (id) ← post_tags → tags (id)

Enforcing relational constraints with ON DELETE rules

FOREIGN KEYS
SQL — Foreign Key Definition
CREATE TABLE posts (
    id BIGSERIAL PRIMARY KEY,
    title TEXT NOT NULL,
    -- Cascading foreign key definition
    user_id BIGINT NOT NULL 
        REFERENCES users(id) 
        ON DELETE CASCADE

ActionBehavior on Parent Delete
CASCADEAutomatically deletes all child rows when the parent is deleted

SECTION 11: SQL JOINS

Practical Multi-Table Queries

Fetching users, their posts, and counting comments with GROUP BY

PRACTICAL SQL
SQL — Joining Users, Posts & Comment Counts
SELECT 
    users.id AS user_id,
    users.name AS author_name,
    posts.title AS post_title,
    COUNT(comments.id) AS comment_count
FROM users
INNER JOIN posts ON posts.user_id = users.id
LEFT JOIN comments ON comments.post_id = posts.id
GROUP BY users.id, users.name, posts.id, posts.title
ORDER BY comment_count DESC;
SECTION 12: INDEXES

What is a Database Index?

Speeding up query reads with B-Tree data structures

INDEXING
SQL — Creating Indexes
-- Single column index
CREATE INDEX idx_users_email 
ON users(email);

-- Composite index (multi-column)
CREATE INDEX idx_tasks_project_status 
ON tasks(project_id, status);

The B-Tree Index

Without an index, finding a user by email requires scanning every single row in the table (Sequential Scan, O(N)). An index provides an O(log N) lookup path.

Indexes Are Not Free

Indexes consume disk space and add write overhead. Every INSERT, UPDATE, and DELETE must also update the corresponding index trees.

QUERY PLAN

SECTION 13: TRANSACTIONS & ACID

Transactions & ACID Guarantees

The four pillars of reliable, enterprise-grade data management

ACID
A

Atomicity

All operations in a transaction succeed, or all fail together. Never half-written data.

C

Consistency

Constraints (unique, foreign keys, types) are strictly enforced before committing.

I

Isolation

Concurrent transactions do not see intermediate, uncommitted modifications.

D

Durability

Committed records are permanently written to Write-Ahead Logging (WAL) on disk.

SECTION 13: TRANSACTIONS & ACID

Transaction Workflow in Action

BEGIN, COMMIT, and ROLLBACK in banking and payment processing

BANK TRANSFER
SQL — Bank Transfer Transaction
BEGIN;

-- 1. Deduct from Alice
UPDATE accounts 
SET balance = balance - 100 
WHERE id = 'alice-123';

-- 2. Add to Bob
UPDATE accounts 
SET balance = balance + 100 
WHERE id = 'bob-456';

-- Commit changes permanently
COMMIT;

-- Or abort on any failure:
-- ROLLBACK;
Transferring $100 between two bank accounts requires deducting from Account A and adding to Account B. If the server crashes midway, a transaction guarantees no money vanishes.
SECTION 14: DATABASE DESIGN

Database Normalization (1NF to 3NF)

Eliminating redundancy while keeping queries clean and maintainable

SCHEMA DESIGN

BAD DATABASE (Denormalized)

users ├─ id: 1 ├─ name: "Dara" └─ posts: "Post 1, Post 2, Post 3" <-- Comma list!

Cannot index individual posts, cannot join on author, cannot maintain referential integrity.

GOOD DATABASE (Normalized)

users (id, name, email) ↓ (1:N via user_id) posts (id, user_id, title) ↓ (1:N via post_id) comments (id, post_id, comment)

Clean, queryable, indexable, cascade-safe.

SECTION 14: DATABASE DESIGN

Production Schema Conventions

Clean naming rules, audit fields, and column constraints

BEST PRACTICES

Naming Rules

Use lowercase snake_case. Use plural table names (users, projects) and singular foreign keys (user_id).

Audit Columns

Always add created_at TIMESTAMPTZ DEFAULT NOW() and updated_at TIMESTAMPTZ DEFAULT NOW().

Explicit Constraints

Prefer NOT NULL whenever a value is required. Always add explicit foreign keys with ON DELETE policies.

SECTION 15: MIGRATIONS

Writing Safe Production Migrations

Executing ALTER TABLE without locking tables or breaking production

ALTER TABLE
SQL — Adding Column Safely
-- Safe: Adding nullable column or column with DEFAULT
ALTER TABLE users 
ADD COLUMN avatar_url TEXT;

-- Safe: Adding column with default (PG 11+)
ALTER TABLE users 
ADD COLUMN role TEXT NOT NULL DEFAULT 'member';

Backwards Compatibility

Never rename or delete a column while existing application versions are running. Deploy in phases: add column -> deploy app -> migrate data -> remove old column.

Never add a NOT NULL column without a DEFAULT on a table with existing rows, as PostgreSQL will reject the migration immediately.
SECTION 16: BACKUPS & RESTORE

PostgreSQL Backups: pg_dump & Restore

Creating logical SQL dumps and restoring them with psql

pg_dump
bash — dump & restore
# Backup database to SQL file pg_dump -U postgres -d myapp > backup.sql # Restore database from SQL file psql -U postgres -d myapp < backup.sql # Compressed custom format (.dump) pg_dump -U postgres -F c -d myapp > myapp.dump pg_restore -U postgres -d myapp myapp.dump

pg_dump (Logical Backup)

pg_dump extracts a consistent snapshot of the database schema and data into SQL statements or custom compressed binary format.

Restoring Data

SQL text dumps are restored using standard `psql myapp < backup.sql`. Custom directory or compressed dumps use `pg_restore`.

SECTION 16: BACKUPS & RESTORE

Disaster Recovery Best Practices

Why an untested backup cannot be trusted in production

DISASTER RECOVERY
Core Engineering Rule: A backup that has never been restored is not fully trusted. You do not have a backup plan until you have verified your restore procedure.

Automated & Scheduled

Schedule automated daily backups and store them in geographically separate object storage (e.g., S3/Cloud Storage) with retention policies.

Point-in-Time Recovery (PITR)

Modern cloud systems like Neon continuously stream WAL logs, allowing you to restore the database to any specific second in the past.

Restore Drills

Regularly spin up a staging database from your latest backup to verify recovery time and data integrity.

Traditional Postgres vs Neon Architecture

Monolithic local disk vs cloud storage pageservers & distributed WAL

ARCHITECTURE COMPARISON

Traditional PostgreSQL

Compute and disk are tightly coupled to a single virtual machine. Upgrades, scaling, and resizing require stopping the server or complex replication.

SECTION 27: CONNECTION POOLING

The Serverless Connection Problem

Why 500 lambda invocations can crash a traditional database

CONNECTION CRASH
Problem: Direct Serverless Connections
500 Serverless Functions (Vercel Lambdas) ↓ 500 separate open TCP connections! PostgreSQL Server (max_connections = 100) ↓ FATAL: sorry, too many clients already! 500 Server Error (App Outage!)

Stateless Function Concurrency

Serverless functions spin up independently on demand. When traffic surges, 500 simultaneous instances open 500 separate PostgreSQL connections.

Postgres Connection Cost

Each direct PostgreSQL connection forks a dedicated backend operating system process consuming ~10MB RAM. The server quickly runs out of memory and rejects connections.

SECTION 31: SEARCH & PAGINATION

Pagination: The LIMIT / OFFSET Problem

Why OFFSET 100000 degrades severely on large production tables

OFFSET CLIFF
Slow OFFSET Query
-- Page 5000:
SELECT id, title, created_at
FROM tasks
ORDER BY id ASC
LIMIT 20 OFFSET 100000;

The OFFSET Penalty

`LIMIT 20 OFFSET 100000` requires PostgreSQL to read, sort, and discard 100,000 rows before returning the 20 requested records, creating high CPU and I/O load.

Data Drift

If new rows are inserted while users paginate, rows shift across page boundaries, resulting in users seeing duplicate items.

SECTION 31: SEARCH & PAGINATION

Keyset (Cursor-Based) Pagination

Consistent O(1) performance regardless of dataset depth

CURSOR O(1)
Keyset / Cursor Query
-- Next page starts immediately after last seen ID:
SELECT id, title, created_at
FROM tasks
WHERE id > 100020
ORDER BY id ASC
LIMIT 20;

How Keyset Pagination Works

Query records where the primary key is greater than the last seen ID: `WHERE id > $last_id ORDER BY id ASC LIMIT 20`. Jumps directly via B-tree index seek.

Execution time on 10,000,000 rows remains identical on Page 1 as on Page 100,000 (~0.1ms).

SECTION 37: 12 COMMON DATABASE MISTAKES

Top 12 Beginner & Production Mistakes

Critical anti-patterns to avoid in professional database management

ANTI-PATTERNS
1. Using Superuser in App

Never connect your app as postgres. Use a dedicated restricted user.

2. Exposing DATABASE_URL

Never prefix with NEXT_PUBLIC_ in your Next.js environment variables.

3. Forgetting Foreign Key Indexes

PostgreSQL does not auto-index FKs; always create them manually.

4. Using TIMESTAMP without TZ

Always use TIMESTAMPTZ to avoid timezone calculation bugs.

5. SELECT * Everywhere

Fetches unused columns, wasting memory, CPU, and network bandwidth.

6. Raw String SQL Concatenation

Always use parameterized queries ($1, $2) to prevent SQL injection.

7. Direct Serverless Connections

Use Neon PgBouncer pooled connection strings to prevent exhaustion.

8. Unchecked UPDATE / DELETE

Forgetting WHERE updates or deletes every row in the table.

9. Untested Backups

A backup never restored is an illusion; drill your restore procedures.

10. Manual Schema Edits in Prod

Always apply schema modifications via version-controlled migrations.

11. Missing Unique Constraints

Relying solely on frontend validation results in duplicate data.

12. High OFFSET Pagination

Use keyset / cursor pagination for fast O(1) performance at scale.
